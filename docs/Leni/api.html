Pré requis LENI

  • Création de la nouvelle instance à partir du dernier événement VIMEET
  • A fournir à VIMEET : L’identifiant de la manifestation IdEvenement. Le compte de connexion à la gateway > Voir Pascal, Franck ou Olivier pour ces deux points
  • Faire créer un compte de connexion à ATLAS et fournir l’URL, login et mot de passe

Créer les champs suivants :

  • "ZL_RDVNONORGANISES": Type TEXTE, longueur illimité, chaine de caractères contenant les rdv non organisés
  • "ZL_JOURNEE(n)", (n) de 1 à 10: Type TEXTE, longueur illimité contenant l'agenda de l'événement (donc créer autant de jour qu'il y en a sur l'événement)
  • "ZL_ACTIF" : Type CHOIX - ACTI (actif) ou INAC (inactif) selon le statut Vimeet (inactif = pas de badge)
  • "ZL_ETATDEPAIEMENT" : Type CHOIX - PA (payé) ou PP (pas payé)
  • "ZL_IDPRODUITPARTICIPANT" : entier ou null
  • "ZL_LEADER_ID": idUtilisateur LENI
  • "ZL_LEADER_SOCIETE": nom de la fiche Vimeet
  • "ZL_LEADER_EMAIL": email participant
  • "ZL_LEADER_NOM": nom participant
  • "ZL_LEADER_PRENOM": prenom participant

LENI mapping des types de participation Types mapping 

Mapping entre Id type Vimeet et champs LENI au format JSON :

{
"states":{ "sheet_state":"ZL_MODERATION" },
"tags":{ ... },
"products":{ ... }
}

Exemple :

{
"states":{ "sheet_state":"ZL_MODERATION" },
"tags":{ "participant_generic_tag_1":"ZL_DATENAISSANCE" },
"products":{ "2576":"ZL_PRODUCT_2576", "2951":"ZL_PRODUCT_2951" }
}

Pour le mapping conditionnel, cf chapitre plus bas dans cette doc.
LENI mapping des champs mapping 

Il s'agit de champs supplémentaires à récupérer sur le template d'inscription our template de présentation. Le mapping se fait avec les tags Vimeet et les noms des champs LENI, au format JSON :

{
  "tag_vimeet": "champs_leni",
  "autre_tag_vimeet": "autre_champs_leni"
}

Exemple : 

{"sheet_state": "ZL_MODERATION", "sheet_template_generic_tag_1": "ZL_THEMATIQUES", "sheet_template_generic_tag_2": "ZL_TypePrestation", "participant_position": "EvenementFonction", "sheet_organization_staff": "ZL_Effectif", "sheet_generic_tag_1": "ZL_ACTIVITE", "sheet_generic_tag_4": "ZL_Emplacement", "sheet_generic_tag_5": "ZL_Commerce", "sheet_generic_tag_6": "ZL_NombreHabitant"}
LENI Mode (get, save ou both) mode  Important : Le mode est à paramétrer en dernier afin que le CRON ait tous les paramètres à disposition.
  • "get" pour uniquement récupérer des données depuis LENI
  • "save" pour uniquement envoyer des données vers LENI
  • "both" pour les deux modes
LENI filtres de l'API (GET) filtres pour filtrer les résultats de l'API, exemple :

[{"selectedFieldId":"CategorieIndividuEvt", "selectedOperator":"IN", "value": ["VISITEUR", "PRESSE"]}]

Cf la documentation fournie par LENI pour le fonctionnement des filtres.
LENI lien pour le badge lien vers le badge

Ce paramètre permet de faire le lien entre un utilisateur Vimeet avec son accès sur vers un site LENI.

Il faut définir à la fois le lien, incluant une position pour l'id de l'utilisateur LENI, et les types de participations concernées par cette possibilité.

Exemple :

{ "link": "https://example.org/account/welcome.html?accesToken=%s", "concerned_type_ids": [1234, 4567] }

Fonctionnement récupération (GET) :

  • une nouvelle inscription non connue par Vimeet est récupérée puis sauvegardées, les mises à jour ne sont pas prises en compte.
  • fréquence de récupération : toutes les 10 minutes.

Etat de l'inscription 

Dans le paramètre supplémentaire "LENI mapping des champs", il est possible grâce au tag "sheet_state" de récupérer l'état de l'inscription depuis LENI :

{ "sheet_state": "ZL_MODERATION" }

La correspondance entre les valeurs LENI et le statuts Vimeet sont :

  • W (en attente) = En attente
  • A (Accepté) = Accepté
  • Y (validé) = Validé
  • R (refusé) = Refusé

Mapping pré-défini quelque soit l'évènement

Champs définis quelque soit l'évènement à gérer entre Vimeet / LENI :

  • "Id": id utilisateur LENI | null si nouvel utilisateur pas connu par LENI
  • "Cab2": idUtilisateur Vimeet
  • "CleExterne": idUtilisateur Vimeet
  • "Civilite": civilité participant
    - MME devient woman pour Vimeet
    - MLLE devient woman pour Vimeet
    - M devient man pour Vimeet
  • "Nom": nom participant
  • "Prenom": prenom participant
  • "Email": email participant
  • "EvenementFonction": tag fonction du participant
  • "EvenementOrigine": si nouvel utilisateur Vimeet, envoyer "API" sinon la valeur récupérée depuis l'API (WEB ou IMPORT)
  • "Societe": nom de la fiche Vimeet
  • "CodePostal": tag code postal
  • "Ville": tag ville
  • "Adresse1" : tag adresse Vimeet
  • "Pays": tag pays
  • "TelephoneFixe" : tag téléphone participant
  • "Mobile" : tag mobile participant
  • "Langue": langue utilisateur
  • "Inscrit" : "Inscrit" si créé par Vimeet, sinon prendre la valeur fournie par l'API
  • "ZL_RDVNONORGANISES": chaine de caractères contenant les rdv non organisés
  • "ZL_JOURNEE1": chaine de caractères contenant l'agenda du 1er jour
  • "ZL_JOURNEE( n )": chaine de caractères contenant l'agenda du n-ième jour selon le nombre de jours de l'évènement
  • "ZL_ACTIF" : ACTI ou INAC ; état de la fiche sur Vimeet (Activé ou désactivée)
  • "ZL_ETATDEPAIEMENT" : PA ou PP ; état de paiement de la fiche sur Vimeet. Si pas de forfait pour la fiche, elle est en état payé.
  • "ZL_IDPRODUITPARTICIPANT" : entier ou null ; il s'agit de l'id produit participant de l'utilisateur

Quelque soit l'évènement, s'il s’agit d’un collègue (à rattacher à un contact existant), les données suivants sont envoyées, contenant les informations du propriétaire de la fiche Vimeet :

  • "ZL_LEADER_ID": idUtilisateur LENI
  • "ZL_LEADER_SOCIETE": nom de la fiche Vimeet
  • "ZL_LEADER_EMAIL": email participant
  • "ZL_LEADER_NOM": nom participant
  • "ZL_LEADER_PRENOM": prénom participant

Données complémentaires envoyées :

  • les champs définis dans le paramètre "LENI mapping des types de participation"
  • les champs définis dans le paramètre "LENI mapping des champs"

Si le champ tagué est une nomenclature, la correspondance sera faites sur la clé de chaque élément de la nomenclature. Il est indispensable que d'importer sur Vimeet les nomenclatures avec les clés des nomenclatures de LENI. Par exemple, si on a cette nomenclature :

  • F1 | Manager
  • F2 | Gérant
  • F3 | Salarié
  • ...
  • F99 | Autre

Mapping conditionnel des types de participation

Le paramètre supplémentaire "LENI mapping des types de participation" accepte maintenant une entrée "condition" pour chaque type de participation, qui est écrit en "ExpressionLanguage", un composant de Symfony : cf la doc sur la syntaxe https://symfony.com/doc/current/components/expression_language/syntax.html

IMPORTANT : le mapping conditionnel ne fonctionne qu'avec le mode "GET" et non "SAVE".

Exemple :

{"424": {"condition": "CategorieIndividuEvt === 'VISITEUR' & ZL_EDT_SECTEUR_ACTIVITE in ['A01', 'A02']" }, "423": {"condition": "CategorieIndividuEvt === 'VISITEUR' & ZL_EDT_SECTEUR_ACTIVITE in ['A07']" }}

NB : tous les champs utilisés dans les conditions hors ceux du "Mapping pré-défini quelque soit l'évènement" doivent être récupérés via le paramètre supplémentaire "LENI mapping des champs". Par exemple ici, on utilise "ZL_EDT_SECTEUR_ACTIVITE". On devrait avoir par exemple dans "LENI mapping des champs" :

{"sheet_generic_tag_4": "ZL_EDT_SECTEUR_ACTIVITE"}

Le mode sans condition, c'est à dire mapping simple de champs : clé + valeur et tous en "ET" est toujours valable, exemple :

{"344": {"CategorieIndividuEvt": "VISITEUR", "ZL_EDT_SECTEUR_ACTIVITE":"A07"}}

On pourrait ré-écrire ce mapping précédent avec une condition sous cette forme :

{"344": {"condition" : "CategorieIndividuEvt === 'VISITEUR' & ZL_EDT_SECTEUR_ACTIVITE === 'A07'"}}

 

Activer sur Vimeet l'envoi d'email de LENI

Il s'agit de la fonctionnalité "SendingRequests" de LENI. Sur Vimeet, dans les paramètres supplémentaires de l'évènement, définir le paramètre "Leni Paramètre SendingRequests". Les CodeCommunication et Id sont fournis par LENI. Les éléments sont disponibles dans la liste des campagnes transactionnelles en affichant les champs ID et CODE.

Envoi d'email lorsque l'utilisateur n'est pas encore connu par LENI

Type Nom Valeur
Leni Paramètre SendingRequests sendingRequests (libellé n'importe pas)

{"sending_request_new_user": [{"CodeCommunication":"XXXX", "Id": "XXX-YYYY-ZZZ"}]}

 

Envoi d'email lorsque le statut de la fiche passe à "Valider"

Si le tag "sheet_state" est défini dans les paramètres de mapping des champs (Cf plus haut chapitre "Etat de l'inscription") et que le statut de la fiche passe de "non validé" (les autres statuts) à "validé"
OU
il n'existe pas d'envoi précédent à LENI (nouveau participant sur une fiche par exemple) et la fiche est en validée
ALORS :

  • le champ "Inscrit" est envoyé avec comme valeur "Inscrit"
  • envoi d'un email, si le paramètre suivant pour l'évènement existe :
Type Nom Valeur
Leni Paramètre SendingRequests sendingRequests (libellé n'importe pas) {"sending_request_sheet_is_validated": [{ "CodeCommunication": "XXXX", "Id": "XXX-YYYY-ZZZ"}]}
